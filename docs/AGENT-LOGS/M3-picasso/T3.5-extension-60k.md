**Decisions taken during the work** (each with the alternative rejected and why):
- **Selection rule.** `evaluated_steps(last) = range(5000, last + 1, 5000)` ∩ the run's
  checkpoints. `EVALUATED_STEPS` is kept as `evaluated_steps(40000)`, pinned verbatim. A missing
  multiple of 5k is skipped with a warning. Rejected: raising on a missing step. The pre-D22 code
  skipped silently, and raising would change the 40k behaviour the ticket freezes.
- **Gate names.** `<run_id><amp>_gate_<early:06d>_<late:06d>.{json,tar}`, 6-digit padding like
  `ema_iter_%06d`, so a lexicographic glob is also step order. The legacy `<run_id><amp>_gate.tar`
  is accepted as 35k/40k and unpacked first. Rejected: a one-off rename on Picasso, which would
  make `main` touch files. Accepted by `main` (e).
- **Gate defaults.** `GATE_EARLY` defaults to `N_ITERS − 5000`, as the ticket says literally,
  not `GATE_LATE − 5000`. Both are validated: they must be positive, multiples of 5k and
  increasing. The launcher resolves the pair and exports it, so the printed pair is the one the
  worker runs.
- **`N_ITERS` guard.** The launcher and the eval worker refuse an `N_ITERS` that is not a positive
  multiple of 5,000, because the final sets are drawn only when the largest step is evaluated.
  The worker also refuses a run whose largest EMA checkpoint is not `N_ITERS`; otherwise an
  extended run submitted with a stale `N_ITERS=40000` would be scored to 60k without any warning.
- **Time rule.** One rule everywhere (`main` ruling a). 40k `off` becomes `09:45:00`, down from
  `10:00:00`; this is recorded in `evaluation_plan.md` §3 footnote ² and §9. Rejected: rounding to
  30 min, which fits 40k but gives 60k fp16 09:30 instead of the ticket's 09:15.
- **Shell logic tested from pytest.** `tests/metrics/test_run_eval.py` sources `common.sh` and
  calls the real functions, and it dry-runs `submit_eval.sh`. Rejected: a Python mirror of the
  arithmetic, which could drift from the shell it claims to test. One test cross-checks the shell
  chain count against `evaluated_steps`.
- **`check_array` light by default, `--deep` = `check_run_dir`** (`main` ruling d). Light mode
  reuses `validate_run`'s `read_metrics_strict`, `check_metrics`, `_check_manifest`, `_check_grids`
  and `_expected_steps`, and adds only a torch-free presence check of the checkpoint files.
  Rejected: always calling `check_run_dir`, which reads ≈ 36 GB for the array on the login node.
- **lr from `config.json`** (`optim.lr`), because the manifest has no lr key (`main` ruling b).
- **Cross-cell recipe.** The comparison is `recipe_of(config.json)` minus `CELL_KEYS` (`main`
  ruling c); `recipe_of` already drops `run_id` and the path/host keys. The reference is the
  majority recipe, and the diff names the keys. Arm keys must also agree within each arm.
  Rejected: comparing against `configs.spectral.arms.get_config` of today's checkout, because a
  later factory change would flag runs that trained correctly.
- **Per-cell recipe hash.** The manifest's `recipe_sha256` must equal the hash of `config.json`'s
  recipe (same canonical JSON as `recipe.recipe_sha256`).

**Assumptions proceeded on** (the rulings (a)–(f) of `main` settled the others; this one is
reported in the final hand-back):
- `validate_run`'s private helpers (`_check_manifest`, `_check_grids`, `_expected_steps`) are
  stable enough to import. If they are renamed, `check_array` fails at import (loudly). §6
  proposes making them public.
