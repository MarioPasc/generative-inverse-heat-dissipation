**Decisions taken during the work** (each with the alternative rejected and why):

- **QOS is `medium_uma`, not `medium`.** The live association is
  `tic_163_uma|long_uma,medium_uma,short`; `medium` exists cluster-wide with identical limits
  (3-day wall, `gres/gpu=23`) but is outside our association and `sbatch --test-only` refuses it
  with `allocation failure: Invalid qos specification` (control run, §4). *Rejected:* keeping
  `--qos=medium` as the ticket and `docs/HARNESSES/picasso.md` §1 both write it — it cannot be
  submitted. *Rejected:* `long_uma` (7-day wall) — 11 h needs no more than the 3-day QOS, and the
  longer QOS has a lower GPU cap on `long` (12) and no benefit here. Messaged to `main`.
- **`cells.csv` is generated, not hand-written.** `make_cells.py` flattens `EXPERIMENT_CELLS` and
  sorts by `(tier, arm, dataset, seed)`; `--check` fails if the committed file is stale and
  `tests/slurm/test_cells.py::test_committed_file_is_not_stale` enforces it in CI. *Rejected:* a
  literal CSV in the repo — it would drift from the config factory silently, and a silent drift
  trains the wrong cell under the right run id.
- **The worker matches its row on the index column, not the line number.** *Rejected:*
  `sed -n "$((TASK+2))p"` — correct today, but a row ever added or removed shifts every cell by
  one with no error anywhere.
- **Idempotence is decided by `DONE` plus the highest `ema_iter_XXXXXX.pt`.** `DONE` is an empty
  marker (`Path(workdir)/"DONE").touch()`), so it carries no step; `_finalise` writes the final
  EMA checkpoint at `final_step` before touching `DONE`, which makes the highest `ema_iter`
  number the step reached. *Rejected:* reading `manifest.json`'s `n_iters` — it records what was
  *requested*, not what was reached, so a TIMEOUT at 30k would look complete. *Rejected:* loading
  `checkpoints-meta/checkpoint.pth` — that needs torch, i.e. a 20 s python start on every skip.
- **Output goes to FSCRATCH, not `$LOCALSCRATCH`.** *Rejected:* the skill's default staging rule —
  a run writes ≈ 40 files over 6.8 h, which is not the thousands-of-small-files pattern the
  manual's §4.9 rule addresses, and staging would break the resume rule: the trainer reads the
  previous submission's rolling checkpoint out of the run directory, which a wiped node-local
  directory would not have. Stated explicitly in the worker's header, per the skill's sanity
  check 15. T5.1's evaluation, which does write thousands of samples, uses `$LOCALSCRATCH`.
- **The launcher repeats every resource flag on the `sbatch` line although the worker has its own
  `#SBATCH` header.** Command-line flags win, the submission is self-documenting in
  `submissions.md`, and a one-off override (`QOS=`, `TIME_LIMIT=`, `MEM=`) needs no edit to the
  worker. *Rejected:* IsalGraph's header-less worker — the worker would then be unusable without
  the launcher, and the probe worker (T3.2) carries its header.
- **The array range is derived from `cells.csv`, and an `ARRAY_SPEC` naming an absent index is
  refused before submission.** *Rejected:* hard-coding `0-29` — a hard-coded count cannot
  disagree with the decode, so it cannot catch a decode that changed (skill checklist 6b).
- **The 2 h job floor needs no grouping here.** Each task is a 6.84 h run, well above SCBI's
  floor, so the array keeps one cell per task.
