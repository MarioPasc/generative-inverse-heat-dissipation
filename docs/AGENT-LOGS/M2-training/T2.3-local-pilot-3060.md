**Decisions taken during the work** (each with the alternative rejected and why):

- **D-T2.3-1. Throughput is read from the logger's own `it_per_s` field (median over the log lines
  at step ≥ 20), not from differences of `wall_s`.** `ihdm/train/logging.py` accumulates
  `_window_dt` over the training steps only, so `it_per_s` is the pure optimisation rate; `wall_s`
  is the elapsed time of the whole loop and absorbs the eval and grid blocks. Taking the wall-clock
  difference instead (rejected) gave 1.70 it/s at batch 2 against the 2.12 it/s of the training
  steps, i.e. it would have reported the cost of the 60-iteration cadence of the sweep rather than
  the throughput the Picasso array is sized from. The sweep's own wall time is reported separately.
- **D-T2.3-2. The batch-6 OOM was re-run once on an idle card before being recorded.** The first
  attempt started three seconds after the batch-4 process exited, so its failure could have been
  contamination from memory the previous process had not yet released. The retry started with
  798 MiB in use (the desktop compositor only) and failed identically, at the same allocation and
  with the same 10.47 GB already allocated by PyTorch. Accepting the first failure without the
  retry (rejected) would have left the single most load-bearing negative result of the ticket
  resting on a possible artefact.
- **D-T2.3-3. Batch 6 was not retried with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`,
  which the OOM message suggests.** That flag changes the allocator, so the resulting peak would
  not be comparable with T2.1's 4.709 GB at batch 2, with the batch-2/4 points measured here, or
  with whatever T3.2 measures on the A100 under the array's default environment. Measuring the
  configuration the array will actually run under was preferred to measuring the best obtainable
  batch on this card. The flag is recorded in §6 as an option for T3.2 if the A100 is borderline.
- **D-T2.3-4. The memory model is fitted as a two-point line through batch 2 and batch 4, and the
  batch-6 OOM is used as an out-of-sample one-sided check, not as a third fitting point.** An OOM
  gives an inequality (the peak exceeds what was free), not a value, so it cannot enter a least
  squares fit; it can and does falsify or corroborate the line's prediction.

**Assumptions proceeded on** (each also messaged to `main` when made):
- The 848 MiB / 798 MiB the desktop compositor holds on this card is not counted by
  `torch.cuda.max_memory_allocated`, so the `gpu_mem_peak_gb` numbers are process-local and
  transfer to a headless A100. If wrong, every extrapolation below is low by ≈0.8 GB, which does
  not change any of the conclusions (batch 16 fits, batch 24 does not).
- The A100 factor of 3–4× is inherited from T2.1 and from D4″; nothing in this ticket measures an
  A100. If the true factor is below 3, every wall-clock estimate below scales up inversely.
