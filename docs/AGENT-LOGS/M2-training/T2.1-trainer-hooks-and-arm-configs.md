**Decisions taken during the work** (each with the alternative rejected and why):

- **`get_label_sampling_function(K, train_level_max_inclusive=False)` gains a second, defaulted
  parameter** and `get_inverse_heat_loss_fn` passes
  `config.model.get("train_level_max_inclusive", False)`. Rejected: computing `K + 1` at the call
  site only (`get_label_sampling_function(config.model.K + 1)`), which would be a one-line diff but
  puts the `high = K + 1 if ... else K` expression that `04` §5 freezes outside the function the
  contract names, and would silently change the meaning of the function's own argument. The default
  keeps the released behaviour for any other caller (there is none outside `losses.py`; checked with
  grep over `sample.py`, `evaluate.py`, `scripts/`).

- **`train.py` is rewritten rather than patched line by line.** The released `train()` body is kept
  in its original order (dirs, model, optimizer, EMA, state, restore, loaders, step fns, forward
  process, sampling fn, loop with train step / preemption checkpoint / eval / checkpoint / sampling)
  and the released `logging.info` lines are kept; only the hook points of `04` §5 change content.
  Rejected: a minimal textual patch, because the checkpoint, sampling and eval blocks are replaced
  wholesale by the ticket (items 6 and 5) and `train.py` is ours to own, unlike `scripts/`.

- **`MetricsLogger.log_train` is called on every step and emits a line only every `log_every`
  steps.** The contract asks for a per-octave loss "averaged over the window since the last log
  line", which requires every step's `losses_batch`/`fwd_steps_batch`. Rejected: a separate
  `accumulate()` call plus a `log_train()` call at log steps, which doubles the call sites in the
  training loop for no gain and makes it possible to forget one.

- **The `loss` field of a `train` line is the mean over the window**, not the instantaneous value of
  the log step, so that it is consistent with `loss_per_octave` (the two are the same average over
  the same set of samples; `mean(losses_batch) == loss` by construction in `get_inverse_heat_loss_fn`).
  Rejected: the instantaneous loss, which is noisier and would not match the octave decomposition on
  the same line.

- **`grad_norm` is measured after the released `optimize_fn` has already clipped**, because
  `torch.nn.utils.clip_grad_norm_`'s return value (the pre-clip norm) is discarded inside
  `scripts/losses.py: optimization_manager`, which is outside the permitted hook lines. The logged
  value therefore saturates at `optim.grad_clip`; a value equal to `grad_clip` means the step was
  clipped. This is documented in `ihdm/train/logging.py`. Rejected: adding a return value to
  `optimization_manager` (an edit to `scripts/losses.py` outside the frozen hook).

- **`save_ema` uses `ema.store / ema.copy_to / <snapshot state_dict> / ema.restore`**, so the saved
  dict contains the model's buffers as well as the EMA'd parameters. Rejected: building the state
  dict from `ema.shadow_params` alone, which silently drops every non-`requires_grad` buffer and
  would give T2.2's `load_ema_model` an incomplete dict.

- **`full_final.pt` is written with the released four keys** (`optimizer`, `model`, `step`, `ema`) by
  `torch.save` directly rather than by calling `scripts.utils.save_checkpoint`, so `ihdm/train/`
  does not import the released module (which imports `cv2` at module level). The format is identical
  and `scripts.utils.restore_checkpoint` reads it.

- **T0.1's `tests/train/test_released_smoke.py` is folded into `tests/train/test_smoke_train.py`
  and deleted.** After this ticket `train.py` is no longer the released file, so a test named
  "released smoke" that only asserts `checkpoints-meta/checkpoint.pth` exists is both misnamed and
  strictly weaker than `test_smoke_train.py`, which runs the same config through the same subprocess
  pattern and asserts the full artefact set. The subprocess + `CUDA_VISIBLE_DEVICES=""` pattern and
  its rationale are carried over verbatim into the new module's docstring. Rejected: keeping it,
  which would add ~40 s of duplicated CPU work to every run of the suite.

- **The finalisation path is idempotent and shared.** After the loop (or immediately, when
  `initial_step > n_iters`) the trainer writes the final EMA checkpoint if it is not already on
  disk, then `full_final.pt`, then `DONE`. This satisfies "`DONE` only after both exist" for a fresh
  run, a resumed run and a re-submitted finished run with the same or a smaller `n_iters`.

- **Two defects found while verifying, fixed here** (both detailed in §6):
  1. `scripts/datasets.get_dataset` matched the released `elif config.data.dataset ==
     "lsun_church":` torchvision branch **before** T0.1's `NPY_DATASETS` hook. Since
     `lsun_church` is one of our four dataset ids, every churches run (12 of the 30) died with
     `ModuleNotFoundError: No module named 'lmdb'` before the first step. Ownership of the file
     was extended to T2.1 by the orchestrator for this fix; the `NPY_DATASETS` check now runs
     first and the released branches are left in place.
  2. `metrics.jsonl` could carry the bare token `NaN`. `json.dumps` writes it for a non-finite
     float, Python reads it back, but `jq`, `pandas.read_json` and every strict parser reject it.
     It was not hypothetical: AMP's `GradScaler` skips the first optimiser steps and leaves
     non-finite gradients behind, so the first line of the real GPU run read
     `"grad_norm": NaN`. The logger now sanitises the record and dumps with `allow_nan=False`.

     `numpy.float64` into `optimizer.param_groups[0]["lr"]`. Since torch 2.6 `torch.load`

     `numpy._core.multiarray.scalar`, so **every resume failed** on the released

  which is the self-consistent statement. What breaks if wrong: only the number quoted in a log line.

  `eval_loss` each batch and logs only the last one. `04` §3.2 says "loss: float (EMA weights, 25 ref

  smoother than the released one; no downstream consumer reads it except the pilot's eyeball check.

## 6. Open questions, risks, follow-ups

- **Defect 1 (fixed here, ownership extended by `main`): `scripts/datasets.get_dataset` shadowed
  the standard-format backend for `lsun_church`.** The released branch
  `elif config.data.dataset == "lsun_church":` opens a torchvision LSUN lmdb store under
  `data/lsun` and was matched before T0.1's `elif config.data.dataset in NPY_DATASETS:`. Because
  `lsun_church` is both a released name and one of our four dataset ids, **12 of the 30 runs** would
  have failed at submission time with `ModuleNotFoundError: No module named 'lmdb'`. The
  `NPY_DATASETS` check is now first; the released branches are untouched and remain reachable for
  the released configs. `tests/train/test_dataset_routing.py` asserts both the loader type for all
  four ids and the branch order in the source, so it cannot silently come back.

- **Defect 2 (fixed here): `metrics.jsonl` could contain the bare token `NaN`.** With AMP the
  `GradScaler` skips the first optimiser steps and leaves non-finite gradients behind, so
  `grad_norm` was `NaN` on the first line of the real GPU run. `json.dumps` emits `NaN`, which
  Python reads back but `jq` and `pandas.read_json` reject. The logger now sanitises every
  non-finite float to `null` and dumps with `allow_nan=False`. **T4.x should know that a `null`
  `grad_norm` means "the gradients were non-finite at that step", normally only during AMP
  warm-up.**

- **Defect 3 (fixed here): every resume failed on `torch.load`.** The released
  `optimization_manager` writes `g["lr"] = lr * np.minimum(step / warmup, 1.0)`, a `numpy.float64`,
  into the optimiser's parameter group. Since torch 2.6 `torch.load` defaults to
  `weights_only=True` and its restricted unpickler rejects `numpy._core.multiarray.scalar`, so the
  released `scripts.utils.restore_checkpoint` raised `UnpicklingError` on any checkpoint this
  trainer wrote. `ihdm/train/checkpoints.py: optimizer_state_dict` coerces the value before saving.
  **Risk for other tickets:** any checkpoint written by the released
  `scripts.utils.save_checkpoint` (T2.2's or T4.x's code, `sample.py`, `evaluate.py`) has the same
  problem; the safe rule is to write optimiser state through this helper, or to load with
  `weights_only=False`.

- **Warning for D4′ and the Picasso probe (T3.2): batch 64 at $192^2$ will very likely not fit an
  A100 40 GB, and batch 32 is borderline.** Measured: 4.709 GB peak allocation at batch 2 with AMP,
  and a hard OOM at batch 8 on a 11.63 GB card. Subtracting the 1.22 GB of persistent state gives
  ≈1.75 GB of activations per sample, which extrapolates to ≈29 GB at batch 16, ≈57 GB at batch 32
  and ≈113 GB at batch 64. The extrapolation is linear and optimistic in one direction (fixed
  workspaces amortise at larger batches) and pessimistic in another (fragmentation grows), so it is
  an order-of-magnitude statement, not a measurement — but the batch-8 OOM is a measurement. Two
  contributing causes worth checking in the probe: `model_code/nn.py: GroupNorm32.forward` casts
  every normalisation input back to fp32 (`super().forward(x.float()).type(x.dtype)`), which
  removes much of AMP's memory saving, and the attention blocks sit at $48^2$ and $24^2$ with
  `model_channels=128`. **Suggested owner: T3.2**, which should measure batch 8, 16, 24 and 32 on
  the A100 before D4′ is closed. Whatever it finds, the value belongs in
  `configs/spectral/arms.py`, not on the command line, for the reason below.

- **`eval.batch_size` does not follow a command-line `--config.training.batch_size`.** The factory
  sets `eval.batch_size = training.batch_size` when it builds the config, but `ml_collections`
  applies `--config.*` flags afterwards, so a CLI override of the training batch leaves the eval
  batch at the factory value. This is why the demo passes both. The probe must set the batch size
  inside `arms.py` (which `04` §2 prescribes anyway); anything that overrides it on the command
  line must pass `--config.eval.batch_size` too. Confirmed with `main`; going into T3.2.

- **Checkpoint storage is 1.5× the D5 estimate.** 233 MB per EMA checkpoint × 8 per run × 30 runs =
  56 GB, plus 1.9 GB of full/rolling state per run ≈ 56 GB more. **Suggested owner: T3.1/T3.3**, to
  confirm the Picasso quota covers ≈112 GB of checkpoints before the array is submitted.

- **Data order is not checkpointed on resume.** The released state dict holds only
  `optimizer, model, step, ema`, so a resumed run replays the data loader from its beginning with
  the same seed. For a 20k-iteration run over 3200 images (62 epochs) this changes which images the
  post-resume steps see, but not the distribution. Fixing it would mean adding a sampler state to
  the released checkpoint format, which `04` §3 freezes. Recorded, not fixed.

- **`grad_norm` is measured after clipping** (the released `optimization_manager` discards the
  pre-clip norm returned by `clip_grad_norm_`, and that line is outside the frozen hooks). A value
  equal to `optim.grad_clip` means the step was clipped; in the demo every step was. If T2.3 wants
  the pre-clip norm for the pilot, it needs a hook in `scripts/losses.py` that `04` §5 does not
  currently allow.
