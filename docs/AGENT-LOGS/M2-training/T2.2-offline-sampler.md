**Decisions taken during the work** (each with the alternative rejected and why):
- **`load_seed_images("train", n, ...)` falls back to sampling *with* replacement when
  `n` exceeds the size of the train split.** The prompt says "n distinct train-split indices";
  `05-metrics.md` §4 asks for 5 000 training-seeded samples while the `lsun_church` train split
  holds 3 200 images and asks for "seeds drawn with replacement". Raising an error instead would
  make the frozen memorisation endpoint unreachable, so the function draws distinct indices while
  it can and switches to replacement (with a `logging.warning`) only when it must. Messaged to
  `main`.
- **Draw order is kept for `source="train"`** (not sorted). `ihdm/train/grids.py` sorts its eight
  fixed seeds, but sorting is meaningless once indices may repeat, and every consumer pairs
  `samples[i]` with `seed_idx[i]` positionally.
- **`reverse_chain` draws its noise with an explicit `torch.Generator`** rather than
  `torch.randn_like` (which the released loop uses and which consumes the global RNG). The ticket
  requires bitwise reproducibility from `request.rng_seed` alone; a global-RNG copy would depend on
  every other torch call in the process.
- **The CLI's device defaults to `config.device` and is overridable with `--device`.** The flag is
  not in the frozen CLI list, but it is additive: the fixture test needs CPU on a CUDA host, and
  `04` §6 warns that CUDA visibility alone changes behaviour. Hard-coding `cuda if available`
  was rejected because it would make the tiny-fixture CLI test either GPU-bound or unrunnable.
- **`load_ema_model` compares the checkpoint's `schedule.sha256` with
  `config.model.blur_schedule_sha256` strictly** (a missing hash on either side is also an error).
  Accepting a missing hash was rejected: the whole point of D12 is that a checkpoint can never be
  interpreted under the wrong schedule.
- **`reverse_chain` accepts `start_level == 0`** and then returns its input unchanged. Raising was
  rejected because the start-level sweep wants the degenerate end of the range to be well defined
  (level 0 = the unblurred seed, zero reverse steps).

**Assumptions proceeded on** (each also messaged to `main` when made):
- The `seed` source is read from `splits.json["seed"]` (40 dataset-level indices) rather than from
  the `split == "seed"` rows of `index.csv`; both agree on the validated `lsun_church` dataset
  (40 rows, 40 subjects) and on the synthetic fixture. If a future dataset lets the two disagree,
  the seed set would change silently.
- A seed subject with several rows must expose exactly one row with `slice == 5`; a subject with a
  single row (photographs) is taken as is. If an MRI dataset drops slice 5 for some subject, the
  loader raises `SamplingError` instead of silently picking another slice.

**Orchestrator ruling (2026-09-22, in reply to the message above):** all three approved as
implemented; additionally "record the seed multiplicity in `request.json` so M's own-seed check
can use it". Implemented as the `seeds` block of `request.json`
(`n_seeds`, `n_unique`, `max_count`, `drawn_with_replacement`, `repeated_idx_counts`).

## 6. Open questions, risks, follow-ups

- **Batch size changes the sample values.** The noise stream is consumed in flat
  `(seed, replicate)` order, so a stack drawn at `--batch 16` is not bitwise equal to the same
  request at `--batch 64` unless `delta = 0` and `prior_noise` is off. Reproducibility therefore
  requires recording `--batch`, which `request.json` does. Severity: low; owner T4.x. An
  alternative (one generator per flat index) would cost one `Generator` construction per sample.
- **`--amp` is implemented but not used by default and not measured on a long chain.** The prior
  draw deliberately stays in float32; only the network evaluations are autocast. Whether a 200
  step chain in half precision drifts is an open question for T2.3/T3.2. Severity: low.
- **The grid sampler of the trainer (batch 8, 200 steps, 192²) peaks near the 12 GB of the 3060**
  and logged `CUDACachingAllocator ... OOM` warnings during my integration run; it recovered.
  Not my code, but the orchestrator should know before T2.3 runs a long local pilot.
- **`load_run_config` trusts `config.json`.** If a run is resumed with a different
  `--config.*` override, the file on disk is the one written at the first step. T2.1's trainer
  rewrites it each time `train()` starts, so the last write wins; a consumer reading an old run
  should check `manifest.config_sha256` against the checkpoint's. Severity: low.
