## 2. Plan and decisions

**Restatement:** Deliver everything the evaluation of the 30 training runs needs on Picasso
except the submission of the array. That is a launcher and workers for a one-writer prepare
job, the plateau-gate job and the 30-task evaluation array, plus an `--amp` flag in
`evaluate_run` whose sample cache never mixes precisions. One A100 timing job measures the
per-run cost under each AMP mode, and those numbers size `--time` and back an AMP
recommendation to `main`.

**Was T3.2's 3.2 s/chain measured with autocast? No.** `docs/RESULTS/picasso_probe.md` §5 says
"**no `--amp`** (matching T2.2's 3060 measurement so the two are comparable)". The T3.2 log §2
agrees ("The sampler was run without `--amp` … An AMP sampler would be faster and is not
measured here"). The measured values were 3.236 / 3.206 / 3.210 s/chain at batch 32 / 64 / 128.
D16's 7.1 A100-h per run therefore holds for `amp=off`. The array is not under-budgeted, and
AMP is a possible saving, not a correction.

**Plan:**
1. Log first; then `--amp {off,fp16,bf16}` in `run_eval`/CLI with a per-precision cache tree,
   `SampleRequest.amp_dtype` for bf16, tests; commit.
2. Stage clean-fid's weights into Picasso `$HOME` (`~/execs/ihdm/cache/`), compute the expected
   seed-list digests of the four datasets locally.
3. Write `slurm/eval/` (common helpers, prepare, timing, gate, array, launcher, README); dry-run
   the prepare script and the timing worker locally on the 3060; commit, rsync, `--test-only`,
   submit prepare + timing (2 submissions, 1 spare).
4. While they queue: the local `--amp` functional test on the pilot, the full test suite, the
   harness section, the evaluation plan skeleton.
5. When the jobs land: fill the timing table, sizing, `--time`, A100-h per mode, recommendation.

**Decisions taken during the work** (each with the alternative rejected and why):
- **D1: one cache tree per precision.** `off` writes to `samples/` + `metrics/`, and the other
  modes write to `samples_amp-<mode>/` + `metrics_amp-<mode>/`. The `off` signature keeps
  `"amp": false`, so existing fp32 caches (the pilot's, T3.4's) are still reused. A
  `request.json` found in a tree under another precision raises `MetricError` and is never
  overwritten, even with `--force`. *Rejected:* keying only the signature. The old code
  **redraws and overwrites** on a signature mismatch, so an fp16 run on the pilot would have
  destroyed its fp32 cache. The per-step `ckpt_*.json` reuse rule (`record exists and set
  reused`) would also have served an AMP LSD to a later fp32 run. *Rejected:* one `metrics/`
  with an `amp` field checked on read. The pilot's fp32 result files would have been
  overwritten by the functional test.
- **D2: `SampleRequest.amp_dtype: str | None = None`.** `None` keeps today's autocast default
  (fp16 on CUDA). *Rejected:* turning `amp` into a string. That would change the type of a
  field other callers (`sample_ckpt`) pass as a bool.
- **D3: the timing job does not depend on `prepare`.** It draws its own `ixi` seed lists into a
  shadow dataset on `$LOCALSCRATCH`, using a rewritten copy of `config.json` with `data.root`
  pointing there. It checks those lists against `expected_seed_lists.csv`, and the shadow
  inputs against the FSCRATCH originals (main's two conditions). *Rejected:*
  `afterok:<prepare>`. It could put two A100 queue waits (≈ 21 h each for array 1) in series.
  *Rejected:* one combined job. It would break the ≤ 2 h timing budget and make prepare's
  reuse by the array awkward.
- **D4: the gate command is `--ckpts <early> --gate <early>,<late>`.** Verified by two tests:
  the final and held-out sets are drawn only when the largest *available* step is in
  `--ckpts`. *Rejected:* `--ckpts all` or `--ckpts 35000,40000`, which cost 5,000 chains
  instead of 1,000.
- **D5: prepare verifies before it writes.** It draws the lists into a local shadow of every
  dataset and compares them with the locally computed digests. The real dataset folders are
  written only if all four match. Exit 3 otherwise, which was checked locally with a tampered
  CSV: no file written.
- **D6: the gate job returns a tar that the array unpacks.** Its two 500-sample LSD sets are not
  redrawn by the array (signature-checked). *Rejected:* discarding them, which wastes about
  0.9 A100-h per gated run.
- **D7: the timing phases run in priority order under a deadline guard, and the gate runs in
  `off` only when it fits.** The order is the LSD sets per mode, then Inception, then the gate,
  then batch 64. Otherwise the gate runs in the fastest measured mode (it reuses that mode's
  7,500 set). *Rejected:* measuring batch 64 on all 500 seeds. That is 1,500 extra chains, and
  T3.2 already showed that s/chain is flat from batch 32 upwards.
- **D8: `PYTHONPYCACHEPREFIX` is exported on the first line of every worker, and
  `ihdm_env_setup` refuses to start python without it.** This follows main's relay of T3.4's
  measurement. No job of mine had run before the fix.

**Assumptions proceeded on** (each also messaged to `main` when made):
- `lsun_bedroom` and `lsun_church` have identical seed lists (`50eda5fa…` / `f9c94619…`). Both
  have a 3,200-image `train` split, and the draw depends only on the split's index array.
  Recorded as a fact, not a defect. If the two splits were meant to differ, T1.x owns that.
- T_tau is not computed in the array (`--a0-final-lsd` is not passed), because the A0 run's
  final LSD is not known when the other arms' tasks run. `lsd_by_step` is in every summary, so
  T5.2/T6.1 can compute T_tau afterwards.
