**Decisions taken during the work** (each with the alternative rejected and why):
- `NpyImageDataset` and `make_loaders` read split membership directly from `splits.json[split]`
  (not by re-deriving from `index.csv`'s finer per-row `split` column) — rejected re-deriving
  because `03-data-format.md` §3 already defines `splits.json["ref"]` as the whole reference set
  (seed subjects included), so `split in {"ref","seed"}` semantics are already the literal content
  of that key; re-deriving from `index.csv` would duplicate logic and risk drift between the two
  files.
- `split_by_subject(subjects, ...)` takes the **per-row** subject array (length N, one entry per
  image, repeats for MRI slices of the same subject) and returns the full `splits.json` dict
  (`train`/`ref`/`seed` **image-index** lists plus the three subject lists) — rejected taking only
  the *unique* subject list and returning subject-level splits only, because `write_dataset`'s
  `splits: dict` argument in the same §6 signature is the full `splits.json` structure with image
  indices, and only the per-row form lets one function produce both without a second helper the
  ticket does not mention.
- `validate_dataset` groups `index.csv` by `subject` and checks each subject's row indices do not
  straddle `splits.json["train"]` and `splits.json["ref"]` — this is the literal reading of "every
  subject's slices in one split" in `03-data-format.md` §6.
- `write_dataset`'s atomic-write temp file is named `images.tmp.npy`, not `images.npy.tmp` as first
  written — `np.save` appends `.npy` unless the given path already ends with it, so a path ending in
  `.tmp` was actually written to `images.npy.tmp.npy`, and the subsequent `Path.replace` to
  `images.npy` raised `FileNotFoundError`. Caught by the fixture-dependent tests on the first real
  `pytest` run (all `ERROR at setup`), fixed before any commit.
- `.gitignore`'s `data/` line was changed to `/data/` (anchored to the repo root) — unanchored, it
  also matched `ihdm/data/` (this ticket's own package directory), which `git add` then silently
  refused to stage. The intended target was only the released code's top-level download cache
  (`scripts/datasets.py: root="data"` for MNIST/CIFAR10). Caught when the first `git add` of
  `ihdm/data/format.py` failed with "The following paths are ignored"; fixed in a follow-up commit
  (`fix: anchor .gitignore's data/ pattern to the repo root`) since the original `.gitignore` commit
  had already landed.

**Assumptions proceeded on** (each also messaged to `main` when made):
- `environment.yml` needs `blobfile` and `opencv-python-headless` in addition to the ticket's list.
  `scripts/datasets.py` (module-level `import blobfile as bf`) and `scripts/utils.py` (module-level

  decision adds an unnecessary dependency; but removing it makes acceptance item 4 impossible as
  the released `train.py` is explicitly out of scope for edits. Messaged `main`.
- `configs/spectral/smoke.py: get_config()` sets **both** the released old-style training-cadence
  keys (`snapshot_freq`, `snapshot_freq_for_preemption`, `log_freq`, `eval_freq`, `sampling_freq`,
  which the unmodified `train.py` reads) **and** the new-style keys named in `04-run-artifacts.md`
  §6 (`ckpt_every`, `resume_every`, `log_every`, `eval_every`, `grid_every`), with matching values,
  since §2 states the general pattern ("kept under the old names for compatibility") and T0.1's own
  acceptance criterion needs only the old names but a later ticket's `test_smoke_train.py` (named in
  §6) will likely want the new ones on the same config object.
- `tests/train/test_released_smoke.py` overrides `config.training.n_iters = 5` on the object
  returned by `smoke.get_config()` (whose own default is `n_iters=6` per §6) rather than adding an
  `n_iters` parameter to `get_config()`, since §6 fixes the signature as `get_config()` with no
  arguments.
- `config.sampling.prior_noise = False` and `config.optim.automatic_mp = False` in the smoke config,
  to keep the CPU 5-iteration smoke run simple and avoid `torch.cuda.amp` code paths on a
  CPU-only run; the arms' factory (T2.1, out of scope here) is the place D3/D3' set these True.
- `configs/spectral/smoke.py: get_config().model.model_channels = 32`, not the ticket's/§6's literal
  `16` — discovered empirically: `model_code/nn.py: normalization()` hardcodes
  `GroupNorm32(32, channels)`, so every channel count anywhere in the U-Net must be a multiple of
  32; with `model_channels=16` model construction raises `ValueError: num_channels (16) must be
  divisible by num_groups (32)`. 32 is the smallest value that satisfies the released, read-only
  `model_code/` and keeps the network tiny (`channel_mult=(1,2)` gives channel counts 32 and 64).
  Messaged `main`. What breaks if wrong: if a later ticket's own smoke-config-derived fixture
  assumes `model_channels=16` literally, it will hit the same crash; the real constraint (multiple
  of 32) should be documented wherever `04-run-artifacts.md` §6 is next touched.
- `tests/train/test_released_smoke.py` runs `train.train(...)` inside a **subprocess** with
  `CUDA_VISIBLE_DEVICES=""` set in that subprocess's environment, rather than calling
  `train.train(...)` directly in the pytest process — discovered empirically: this worktree's host
  has a GPU (RTX 3060), and `model_code/utils.py: create_model` wraps the model in
  `torch.nn.DataParallel(model, device_ids=None)`, which auto-detects CUDA devices independently of
  `config.device`. With a GPU present, `device_ids` defaults to `[0]`, so `DataParallel.forward`
  scatters the input batch to `cuda:0` while the model's parameters stay on the CPU device set by
  `config.device`, raising `RuntimeError: Expected all tensors to be on the same device, but found
  at least two devices, cuda:0 and cpu!`. Patching `torch.cuda.is_available()` in-process was
  rejected because `torch.cuda.device_count()` is `functools.lru_cache`-decorated in this torch
  version and its result is cached for the life of the process, so masking CUDA after any earlier
  CUDA query in the same pytest session (e.g. another test importing torch and touching CUDA) would
  not reliably take effect; a fresh subprocess with the environment variable set before Python
  starts sidesteps this entirely. This also matches the ticket's own resource constraint ("The GPU
  may be used only for the one-line CUDA check; nothing else"). Messaged `main`. What breaks if
  wrong: if a later ticket's real GPU training run also uses `create_model` unmodified, the same
  `device_ids` auto-detection applies there too, but is *wanted* there (real training runs on GPU);
  this only matters for a config that explicitly asks for CPU on a GPU-equipped host.
