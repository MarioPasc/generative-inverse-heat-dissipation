### Decisions taken during the work

- **D-T4.2-1 — `sample_seed_idx` indexes rows of the `train` array handed in, not rows of the
  dataset.** The contract says "`sample_seed_idx` gives each sample's seed index into `train`",
  while the sampler's `seed_idx.npy` holds *dataset* indices (`splits["train"]` values, e.g.
  3376 for a 3200-row training split). The two cannot both be true. `train_subjects` is a list
  aligned with `train` (length `n_train`) and `per_sample_nn` returns positions in `train`, so
  the only self-consistent reading is: everything is a position in the `train` array, and the
  caller maps dataset index → row position once. Validated (`0 <= sample_seed_idx < n_train`),
  documented in the docstring, and done explicitly in the integration test and in the pilot
  script. Rejected: accepting dataset indices — then `train_subjects[sample_seed_idx[y]]` would
  index the wrong subject whenever the training split is not the identity map, silently.
  **T4.3 must do this mapping** (`np.searchsorted(splits["train"], seed_idx)` when the split is
  sorted, which it is for the frozen datasets).
- **D-T4.2-2 — `dct_lowpass` returns `float32`, computing the transform in `float64`.** The
  contract freezes the output dtype ("float32 in [0,1] -> same"). The low-passed copies of the
  3 200-image training split are 472 MB at `float32` and 944 MB at `float64`, and
  `memorisation_ratio` holds two of them at once for $M_{lp}$; the DCT itself is done in
  `float64` because the round trip `dct → multiply → idct` in `float32` costs ~1e-6 relative,
  which would eat most of the 1e-5 budget against `DCTBlur`. Measured agreement with the
  released `DCTBlur` is ≤ **2.4e-7** (§4), i.e. 40× inside the budget.
  Rejected: returning the input dtype — `memorisation_ratio`'s peak memory would then depend on
  what the caller passed.
- **D-T4.2-3 — the shared stack conversion (`to_float_stack`, `remove_dc`) lives in
  `lowpass.py`.** All three of my modules need "accept uint8 or float, convert once to float32
  in [0,1], raise `MetricError` on rank/squareness/finiteness"; `spectral.py` has a private
  `_as_stack` + `_DcRemoved` that I may not touch and whose chunked-adapter form does not fit a
  torch consumer (it yields `float64` and is read-only by index). `lowpass.py` is the lowest of
  my three layers and the other two already import `dct_lowpass` from it, so the helpers sit
  there with two concrete users each (`02` §1: no abstraction without two concrete users).
  Rejected: a new `ihdm/metrics/_images.py` — outside my ownership list; copying the helpers
  into all three modules — the ticket forbids duplicating helpers.
- **D-T4.2-4 — `nn_distances` holds the whole corpus on the device and chunks the queries
  only.** At the array's scale the corpus is 3 200 × 36 864 `float32` = 472 MB, which fits
  beside a 295 MB query set and a 3.3 MB distance block on the 12 GB GPU (measured peak
  **0.960 GiB allocated, 1.393 GiB reserved**, §4). Chunking the corpus as well would either
  re-upload every query chunk per
  corpus chunk or keep a running `(Q,)` minimum across two nested loops, for no benefit at any
  size this experiment reaches. If the corpus ever does not fit, the OOM path (below) catches
  it. Rejected: nested chunking — complexity with no user.
- **D-T4.2-5 — TF32 is switched off around every `torch.cdist` / `pca_lowrank` call and
  restored afterwards.** `torch.cdist` at `p = 2` uses the matrix-multiply form
  $\|a\|^2 + \|b\|^2 - 2a\cdot b$ for more than 25 rows, so the GPU result is only as accurate
  as the matmul. Measured on the real problem (the 400 `ref` images against the 3 200-image ixi
  training split at $192^2$, nearest neighbours of median 31.95): **TF32 off, the CPU and CUDA
  paths agree to 6.1e-5; TF32 on, they differ by 2.1e-2**, 345× outside the 1e-4 the harness
  asks for. Ampere's TF32 default is off in
  torch 2.14, but it is a global flag any caller (or a future `evaluate_run`) can flip, so the
  functions set it themselves. Rejected: `compute_mode="donot_use_mm_for_euclid_dist"` — it
  materialises `(chunk, C, D)` = 30 TB at the array's scale.
- **D-T4.2-6 — the train/held-out disjointness check hashes the *converted* `float32` bytes**
  (`blake2b`, 16-byte digest, one digest per image) rather than comparing indices, because the
  contract says "assert no overlap with train by hash" and the function never sees indices.
  Measured cost is 0.58 s for the 3 600 images of a real run at $192^2$. A collision would need
  two distinct $192^2$ images with
  the same 128-bit digest. Rejected: comparing raw `uint8` bytes — it would miss an overlap
  between a `uint8` corpus and a `float32` copy of the same images, which is exactly the shape
  `evaluate_run` can produce.
- **D-T4.2-7 — `pca_around_seed` uses `torch.pca_lowrank`, not `scipy.sparse.linalg.svds`.**
  The contract allows either and asks for one justified choice. The training matrix is *dense*
  3 200 × 36 864 (472 MB `float32`); `svds` is an ARPACK/PROPACK iterative solver for sparse
  operators and would run in `float64` (944 MB) on the CPU, whereas `pca_lowrank` is the
  randomised range-finder of Halko, Martinsson & Tropp (SIAM Review 53(2), 2011,
  doi:10.1137/090771806) with `niter = 4` power iterations, runs in `float32` on the same device
  the rest of the module already uses, and is the algorithm `05-metrics.md` §6 names
  ("the first 2 components via randomised SVD"). Measured on the pilot: 0.48 s on the GPU for
  the 3 200 × 36 864 fit.
- **D-T4.2-8 — the component signs are fixed by a deterministic convention** (the entry of
  largest magnitude of each component is made positive). `pca_lowrank` draws its own Gaussian
  test matrix, so without a sign convention the scores of two runs — or of the CPU and GPU
  paths — differ by a sign per component and the "PCA scores reproducible" identity is
  meaningless. The convention is a property of the subspace, not of the draw. `rng_seed` is
  still honoured (`torch.Generator` passed through a local `torch.manual_seed` guard) so the
  fit is bit-reproducible on one device.
- **D-T4.2-9 — `within_seed_diversity` uses the biased (`1/M`) within-seed variance the spec
  writes**, i.e. $D = \frac1M\sum_m \|y_{sm} - \bar y_s\|^2/(W^2-1)$, whose expectation under
  $y_{sm} = x_s + \varepsilon$, $\varepsilon \sim \mathcal N(0, v I)$ is $v\,(1 - 1/M)$, not $v$.
  The spec (§3) freezes the $1/50$ form and the number is only ever compared *between arms* at
  the same $M = 50$, where the factor cancels. The test therefore asserts $v(1 - 1/M)$ within
  5% and the docstring states the bias. Rejected: silently switching to $1/(M-1)$ — it would
  make the implementation disagree with the frozen formula of `05` §3.
- **D-T4.2-10 — `M` and `M_lp` raise rather than return a non-finite number when the held-out
  median distance is zero**, and `within_seed_diversity` raises when `n_per_seed < 2` (a single
  sample per seed has no within-seed variance to measure). The contract asks for no `nan` and
  no `inf`; "undefined" is a caller bug, and `02` §3 asks for fail-fast validators.
- **D-T4.2-12 — `nn_distances` subtracts the corpus mean image from both sides before the
  `cdist`.** A Euclidean distance is invariant to a translation applied to both sets, so this
  changes no number in exact arithmetic; what it changes is the conditioning of the
  matrix-multiply form, whose cancellation error scales with the part of $\|a\|^2$ the two sides
  share — and on registered MRI, where every image is a brain in the same atlas space, that
  shared part is most of the energy. Measured on 1 000 ixi training images at $192^2$: the
  distance of an image to its own copy falls from 0.094 to 0.038, against real nearest
  neighbours of 26 to 48, and every other distance is unchanged to 1e-5. Found because the
  "exact copies have distance zero" test failed at an absolute threshold of 1e-3 (§4). Rejected:
  leaving it out and loosening the test only — the floor enters `M` directly in the regime the
  metric exists to detect (a model that *does* copy).
- **D-T4.2-13 — `ihdm.metrics.diversity` imports `resolve_device` and `float32_full_precision`
  from `ihdm.metrics.memorisation`.** Both torch-using modules need the same two conventions and
  the ticket forbids duplicating helpers. The alternatives were: a new `ihdm/metrics/_torch.py`
  (outside my ownership list), or putting them in `lowpass.py` (which would drag `torch` into a
  module that is otherwise pure `scipy`/`numpy` and is imported by both others). The dependency
  `diversity -> memorisation` is acyclic and is stated in both module docstrings.
- **D-T4.2-11 — `PcaResult.components` has shape `(n_components, H, W)`** (component *images*,
  directly plottable by T6.1's figure) while `mean` is `(H, W)` and the three score arrays keep
  the sample layout of their inputs (`(C, k)`, `(S, k)`, `(S, M, k)`). The contract does not fix
  the component layout. Orthonormality is asserted on the flattened components.

**$M$ came out above 1, not below, and the ticket's expectation ("well below 1") is wrong for
this checkpoint.** The evidence that this is the model and not the metric: the control on real
held-out images gives $M = 1.0014$ and $M_{lp} = 0.9921$; the nearest training image is never the
sample's own seed (0 of 46); each sample is 67.1 from its own seed and 56.6 from its nearest
training image, i.e. *further from the seed than from a stranger*; and the samples carry 57% more
variance than the `ref` images in the $\sigma_B = 16$ band (0.0639 vs 0.0406) while real
registered brains sit only 3.96 apart there. A 750-iteration checkpoint is 1.9% of a run and its
samples are simply off the data manifold. The consequence for the report is stated in
`metrics_bracket.md` §5.1: **$M$ is not a one-sided statistic** — $M \ll 1$ is copying, $M \gg 1$
is a model that has not converged, and $M$ is only readable as "copying or not" once LSD and KID
say the run fits.

The PCA panel says the same thing more legibly: the four seeds sit at PC2 $= +3$ to $+23$ and all
four sample centroids land in $(-4, +3) \times (-15, -9)$, 1.5 training standard deviations away
in a common direction, with a within-seed spread of 3–7% of the training standard deviation.
Mode collapse plus a systematic offset, not copying.

## 6. Open questions, risks, follow-ups

- **18 of the 64 training-seeded pilot samples are not seeded from the training split.** Verified:
  `_runs_local/t41_lsd_samples/seed_idx.npy` holds 64 dataset indices, of which 18 are not in
  `splits["train"]` (they are in `splits["ref"]`, and 6 of those in `splits["seed"]`, i.e. the
  held-out seed subjects). `seeds.npy == images[seed_idx]` holds exactly, so the file is
  self-consistent; what does not hold is that the draw is reproducible — re-running
  `load_seed_images(ixi, "train", 64, rng_seed=0)` today returns a completely different index set,
  all of it inside `splits["train"]`. The `seed` source of the same sampler *does* reproduce
  exactly (`t41_seed_samples/seed_idx.npy` = `[5, 35, 195, 275]`, verified), so the problem is
  confined to the `rng.choice(pool, n, replace=False)` draw of `ihdm/sampling/seeds.py:
  _train_indices`. I could not reproduce the recorded draw from any candidate I tried
  (`choice` over the train pool, over the sorted train pool, over `arange(4000)`,
  `permutation(4000)[:64]`, `integers`), `ihdm/sampling/seeds.py` has not changed since the
  sampling commit `69b13d7`, `splits.json` and `images.npy` were last written at 12:09:20 against
  a 12:19:02 sampling, and `numpy` 2.4.6 has not been reinstalled since 2026-09-22. **I therefore
  report the facts and not a cause.** Severity: high for reproducibility, low for the code —
  D17 already requires the 500 intermediate seeds to be *written to a file*
  (`eval_seeds_500.npy`) and reused, which is exactly the defence; the same discipline should be
  extended to the 2 000-seed final set, and `sample_ckpt` should refuse indices outside the split
  it claims to draw from. Meanwhile T4.2's pilot numbers use the 46 samples that *are*
  training-seeded, and `memorisation_ratio` raises if a caller hands it a `sample_seed_idx`
  outside `train`. Owner: `main` / T4.3 / whoever owns `ihdm/sampling/seeds.py`.
- **`ihdm/metrics/__init__.py` does not export the three new modules**, because it is not in my
  ownership list. T4.3 must either import from the submodules
  (`from ihdm.metrics.memorisation import memorisation_ratio`) or `main` adds six names to the
  package `__init__`. Low severity, one line of work, but it is a visible asymmetry with T4.1's
  spectral exports. Owner: `main`.
- **`MemResult.per_sample_nn` and `per_sample_d` are arrays, and `write_json` refuses nothing
  about them but will inline 2 000 numbers per run.** T4.3 should write the summary scalars to
  `final.json` and keep the per-sample arrays as `.npy` beside it, or the result files stop being
  readable. Low severity. Owner: T4.3.
- **`seed_nn_fraction` needs `sample_seed_idx` in *rows of `train`*, not dataset indices**
  (D-T4.2-1). The mapping is three lines and is written out in the docstring and in the
  integration test, but it is the one place where T4.3 can silently produce a wrong number rather
  than an exception (a dataset index that happens to be a valid row). Medium severity. Owner:
  T4.3.
- **`M` is not one-sided** (§5). If the report quotes "M closer to 1 is better" it will be wrong
  in both tails. Medium severity for interpretation, none for the code. Owner: T6.1.
- **The `cdist` matrix-multiply floor is `sqrt(eps_32) |a|`**, measured at 0.038 on the ixi
  training split at 192² against real nearest neighbours of 26–48 (0.1%). It is harmless for `M`
  and for `seed_nn_fraction` as long as the corpus holds no exact duplicates of each other; if a
  dataset ever does, the `argmin` between two identical corpus images is arbitrary. Low severity.
