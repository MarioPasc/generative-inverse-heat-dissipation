**Decisions taken during the work** (each with the alternative rejected and why):
- **Option name and storage.** `EvalRequest.inception_steps: tuple[int, ...] | None` and
  `--inception-steps 45000,50000,55000,60000`. At each listed step the step's LSD set is scored by
  the existing `_inception_record` (unchanged) and `_memorisation_record` (gained a `prefix`
  keyword, default `"final"`, so the final record's file names and keys are as before); the blocks
  go into `ckpt_<step>.json` as `inception` and `memorisation`, the per-sample arrays into
  `ckpt_<step>_memorisation_per_sample_{d,nn}.npy`, and the summary gains `inception_by_step`,
  `memorisation_by_step` and `sampling.inception_steps` only when the option is given.
  Alternative rejected: a separate `inception_<step>.json` per step (one more file type for
  every consumer; the ticket asks for the block inside `ckpt_<step>.json`).
- **Validation.** Every listed step must be among the `--ckpts` selection (no LSD set otherwise),
  the list must be non-empty, and the option is refused with `--skip-inception`. Alternative
  rejected: silently adding missing steps to the selection (changes `checkpoint_steps` of the
  summary behind the user's back).
- **Reuse.** A ckpt record that already holds both blocks is kept when its LSD set was reused,
  the request is not forced and the stored block has the same `k` and `n_boot`; a record written
  without the option is completed in place from the reused set (tested).
- **Final set and held-out set.** The job keeps `--final-from-lsd`, so `final.json` at 60k is
  computed on the same 500-seed set as the 60k per-step block (the per-step block is the one the
  reading uses; the two agree up to the Inception extractor's run-to-run jitter, smoke: KID
  0.257516 vs 0.257519). `_evaluate_final` always draws the held-out set; the job uses T7.2's
  40 × 5 (200 chains, ≈ 8 min at 192²) rather than the smallest allowed value, so D_pix and the
  inherited band of the baseline at 60k are comparable with the δ-sweep row of the same run.
  Alternative rejected: a new "skip held-out" option (another change to the final path, which
  the contract says stays unchanged).
- **Baseline samples redrawn, not reused from the production tar.** The production evaluation
  (`~/execs/ihdm/eval/lsun_church_A0_s1_amp-fp16.tar`) holds signature-identical LSD sets at
  45k–60k. Redrawing costs ≈ 1.4 A100-h but gives the three runs one identical code path and job;
  the production LSD values serve as an anchor instead (`photo_collect.BASELINE_LSD_ANCHORS`,
  tolerance 0.003 as in T7.2).
- **Seed-list digests.** Computed locally exactly as `prepare_eval.py` phase 1 does
  (`_shadow_dataset` of symlinks in the scratchpad + `ensure_seed_lists`), never writing into
  the local dataset directories; the same procedure reproduces the frozen `lsun_church` row.
  `lsun_church_r128`'s `splits.json` is byte-identical to `lsun_church`'s (T7.1), so its lists
