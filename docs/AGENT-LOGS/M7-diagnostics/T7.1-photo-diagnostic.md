**Decisions taken during the work** (each with the alternative rejected and why):

- **`log_W2_128` is appended with a new `build_schedules --add <name>` path, not by a full
  rebuild.** The full rebuild (`build`) rewrites every entry of `schedules.json` (new `created`,
  new `git_sha`) and re-fits the five matched schedules; the ticket requires every existing entry
  byte-identical. `--add` runs the same `_entry → build_schedule → log_schedule → save_schedule`
  path that built `log_W2` and re-serialises the index with `build`'s format
  (`json.dumps(indent=2, sort_keys=True) + "\n"`), so the diff is 23 insertions, 0 deletions.
  Rejected hand-writing the entry (no provenance, easy to get the hash wrong) and adding the name
  to `SCHEDULES` (a later `--force` rebuild would then re-stamp it with the frozen ones).
- **`TERMINAL_BLURS` gains 64.0** rather than a separate validator for the diagnostic: the only
  consumer is `_structural_problems` (shared by `save_schedule` and `validate_schedule`), and 64
  is the W/2 rule at width 128, not a new kind of schedule. 50 px is still rejected (tested).
- **The schedule was built after committing the code that builds it** (`c0d9f66`), so the
  entry's `git_sha` names a commit that contains the builder.
- **Image side per dataset is a table in the factory (`_IMAGE_SIZE`, default 192), and the
  schedule per `(arm, side)` (`_SCHEDULE_AT_SIZE = {("A0", 128): ("log_W2_128", 64.0)}`).**
  Rejected reading `meta.json.image_size` inside `get_config`: it would make every config build
  depend on the data disk (the tests and the 30 production configs build without data) and add a
  failure mode to cells that never needed one. An integration test checks the table against the
  built datasets instead.
- **`DIAGNOSTIC_DATASETS` and `DIAGNOSTIC_CELLS` are separate from `DATASETS` /
  `EXPERIMENT_CELLS`.** `slurm/array/make_cells.py`, `tests/slurm/test_cells.py` and the
  analysis code enumerate the 30-run tables; adding the ids there would change them.
  `PHOTOGRAPH_DATASETS` does gain the two ids (only the A2p rule reads it; the A0-only
  restriction in `_ARMS_BY_DATASET` is what refuses the other arms).
- **30-cell regression test against the base commit's factory loaded from git**
  (`git show 48363e2:configs/spectral/arms.py`, imported under its own module name), compared
  through `ihdm.train.manifest.config_sha256` and `config_to_json` for all 30 runs, both as the
  factory returns them and after the array's `--config.seed` / `--config.training.n_iters=60000`
  overrides. Rejected a committed table of golden hashes: `config_sha256` covers
  `data.root`, `model.blur_schedule_file` (an absolute path) and `device`, so golden hashes would
  need normalising and would then no longer be the trainer's hash. The test skips (not fails)
  outside a checkout that holds the base commit; a guard asserts the loaded module really is the
  pre-T7.1 factory (`DIAGNOSTIC_CELLS` absent).
- **r128 rows are read back from `lsun_church/index.csv` `source` (shard, row), not
  re-selected by the acceptance rule.** One pass over the shard (`select_rows`) yields exactly
  those rows in order; row identity is then proven on every row by recomputing T1.2's 192² crop
  and requiring pixel equality with `lsun_church/images.npy` (the build aborts otherwise).
  Rejected re-running `collect_photos` with target 4000: it would reproduce the same rows only
  as long as the acceptance rule and the dedup never change.
- **r128 geometry is torchvision's** (long side `int(128·long/short)`, offset
  `int(round((side−128)/2))`) with LANCZOS and luminance first, as the ticket fixes; a test
  checks pixel equality with `transforms.Resize(128, LANCZOS)` + `CenterCrop(128)` on 7 shapes.
  Rejected reusing `_resize_short_side` / `_centre_crop` (rounding and floor), which differ from
  the paper's loader by up to one pixel of framing.
- **n32k layout: idx 0–3999 are `lsun_church` byte for byte, idx 4000–32799 the new rows**
  (approved by `main`). `ref`/`seed` identity is then an array equality the builder asserts.
- **N = 32,800, not 32,840** (confirmed by `main`): `seed ⊂ ref`, so 32,000 train + 800 ref.
- **No raw PNGs for the diagnostic datasets.** T1.2's `NATURAL_CONTROLS/lsun_church/` is
  numbered by test-shard row; train-shard rows would collide with those names, and 28,800 extra
  files buy nothing that `index.csv.source` (shard + row) does not already give.
- **n32k near-copy filter (decision (b) of `main`, 2026-10-01).** The HF train shard holds
  re-encoded copies of `ref` images that SHA-1 cannot see (6/800 `ref` images had one among the
  first SHA-1-only 28,800 rows; `lsun_church`'s own train split has 0/800). A new row whose
  32×32 mean-pooled thumbnail has Pearson r > 0.95 with any of the 800 `ref` images is rejected
  after the SHA-1 check and replaced by the next shard row. Implemented as an optional `screen`
  callable of `collect_photos` (default `None`, which adds no count key, so T1.2's outputs are
  unchanged) and `NearDuplicateScreen`. Rejected (a), the spec's SHA-1-only rule, because the
  dataset would then differ from `lsun_church` in a second property (0.75 % of `ref` with a
  near-copy in train).
