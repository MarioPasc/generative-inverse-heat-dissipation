**Decisions taken during the work** (each with the alternative rejected and why):

- **D-T1.3-1 — `fit_alpha` keeps the analysis scripts' window (`lo_frac=0.10`, `hi_frac=0.70`).**
  `control_profile.fit_alpha` bins `P` on integer DCT radii `b = 1 … N-1` (mean of `P` over
  `b - 0.5 <= n < b + 0.5`) and fits `log P` on `log b` over `0.10 N <= b <= 0.70 N`. At
  `N = 192` that window is `b ∈ [20, 134]`, i.e. **10.0 – 67.0 cycles per image**. The ticket's
  own text (`T1.3` §1) says "`1 <= n/2 <= 48` cycles per image, the same range as the analysis
  scripts"; the two statements disagree, and the delegation prompt's frozen contract resolves it
  in favour of the scripts ("the same radial range the analysis scripts use (read
  `control_profile.py`)"). The ported window is therefore the headline; the ticket's window
  (`b ∈ [2, 96]`, 1–48 c/img) is reported as a second column of the α table so nothing is hidden.
  Rejected: silently using 1–48 c/img — it would not reproduce the archived α values and the
  checklist compares against them.
- **D-T1.3-2 — the last octave bin is closed at 96 cycles per image (DCT radius 192), not at the
  analysis scripts' `N - 1 = 191` (95.5 c/img).** `05-metrics.md` and the delegation prompt both
  freeze `[64, 96]`. The difference is the annulus `191 <= n <= 192`, which carries < 0.02 % of
  the variance; the archived table's last column is therefore labelled `64-95.5` and mine
  `64-96`. Rejected: reproducing `N - 1` — it would contradict the frozen metric spec that T4.x
  will consume.
- **D-T1.3-3 — `mode_power` zeroes the DC mode, the original does not.** `T1.3` §1 requires
  "DC set to 0"; every consumer in the analysis scripts (`residual_norms`, `matched_schedule`,
  `inherited_share`, `octave_shares`) zeroes or excludes it anyway. The integration test compares
  the two after zeroing `P[0, 0]` on the original's output. Rejected: keeping the DC term — the
  ticket's contract asks for it and an un-zeroed DC would silently change `inherited_share`.
- **D-T1.3-4 — `schedules.json` carries `null` for `fitted_on`, `n_images`, `images_sha256` and
  `spread` on the two log schedules.** A log schedule is not fitted on any split, so there is no
  image count, no image hash and no "per-level removed variance of the fitting split". `04` §1
  spells "or null" only for `fitted_on`; extending it to the three derived fields is the honest
  reading. The crossover table in `data_profile.md` reports the log schedule's spread on each of
  the four datasets, which is the quantity the design actually uses. Rejected: writing `3200` and
  an arbitrary dataset's hash — it would assert a provenance that does not exist.
- **D-T1.3-5 — `mode_power` is computed two-pass in float64** (mean image first, then the DCT of
  the centred chunks, accumulating the sum of squares), instead of the original's one-shot
  `dctn(...).var(axis=0)`. The original holds the whole `3200 × 192 × 192` DCT in memory (940 MB
  in float64) and `np.var` on float32 coefficients loses digits on the coarse modes whose mean
  dominates. The two forms are algebraically identical; the integration test checks them to
  `rtol = 1e-6` on a random field. Rejected: the one-shot form — memory and precision.
- **D-T1.3-6 — the bisection of `matched_schedule` is run on the *grouped* spectrum** (modes are
  grouped by their value of `i² + j²`, which is what `λ` depends on, and their power summed).
  The marching sum `Σ (d_{k-1} - d_k)² P` is unchanged up to summation order, and the inner loop
  shrinks from 36 864 to ~12 000 terms. The iteration counts of the original (80 outer geometric
  bisections on the target, 60 inner bisections per level) are kept exactly so the integration
  test against the original passes at `rtol = 1e-6`. Rejected: fewer iterations — it would break
  bit-level agreement with the released procedure.
- **D-T1.3-7 — `ScheduleSpec` orders its fields `(kind, sigma_max, sigma_min=0.5, K=200,
  fitted_on=None)`.** The ticket writes `ScheduleSpec(kind, sigma_min=0.5, sigma_max, K=200,
  fitted_on)`, which is not a legal dataclass signature (a defaulted field cannot precede a
  required one). Every call site uses keywords.

## 6. Open questions, risks, follow-ups

- **[for `main`] Item (ii) fails on IXI (3.96 % against 3 %).** Severity: medium. The harness
  says the orchestrator decides. The evidence above says the excess is one mode, an
  anterior–posterior intensity ramp between subjects, i.e. a bias-field / intensity-
  harmonisation residue of T1.1's pipeline rather than coarse anatomy. Options, none of which
  this ticket took: accept and restate the threshold on the registered data; ask T1.1 for an
  N4-style bias correction or a per-slice ramp removal; or keep the threshold and record the
  failure in the report. Note that removing a between-subject ramp would *also* change
  `ixi_W2` and `ixi_W8`, so any such change means rebuilding the frozen arrays.
- **[for `main`] Item (iii) now holds by 1.09×, not ≈ 6×.** Severity: medium for the
  interpretation, none for the code. The IXI log-schedule spread fell from 51× to 8.7× and the
  Bedrooms one is 8.0×, so "the log schedule is much worse on MRI than on photographs" is no
  longer a large effect on the registered data; the OASIS-1/Churches contrast (15.1× vs 3.8×)
  still is. The proposal's Methods should quote 8.7×/15.1× against 3.8×/8.0×, not 45×/84×
  against 14×.
- **[for `main`] The ticket's own α window contradicts the analysis scripts.** Severity: low,
  resolved by the delegation prompt (decision D-T1.3-1). Over the ticket's stated 1–48 c/img
  window IXI's α is 2.17 rather than 3.22, because the brain spectrum is curved and that window
  is dominated by its flat coarse end. Both columns are in the report; if the report's Methods
  quote a window, it must be the 10–67 c/img one.
- **`schedules.json` uses `null` for `n_images`, `images_sha256` and `spread` on the two log
  schedules** (decision D-T1.3-4). Severity: low. If a consumer (T3.x manifests, T4.x tables)
  expects a number there, say so and I will put `3200` and the fitting dataset's hash behind a
  `fitted_on: null` flag instead.
- **`validate_schedule` reads a flat `schedules.json`** (`{"<name>": {...}}`), the literal
  reading of `04` §1 ("per name: …"). If any consumer expects a `{"schedules": {...}}` wrapper,
  it is a one-line change in `ihdm/spectral/schedules.py`.
- **The matched march costs 45 s per array at $192^2$** (229 s for the five). Rebuilding the
  frozen set after any data change is cheap; there is no need for a cache.
