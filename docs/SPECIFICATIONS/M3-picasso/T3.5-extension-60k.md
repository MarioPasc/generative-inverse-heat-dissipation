# T3.5 — Extension of the 30 runs from 40k to 60k by resume (no retraining)

Milestone M3 · mode: single · model: opus55-high · depends on: T3.4, T5.1, D22 · the archive and
the two submissions are `main`'s steps (§ Procedure), the code and tests are the agent's

## Why

Decision D22 (`00-overview.md`, Mario, 2026-09-26) reverses D21 (a): **every run is extended to
60,000 iterations**, as the pre-registered gate asked (IXI 35k→40k CI above zero). The extension
continues each run from its rolling checkpoint at 40k, so nothing is retrained. The code already
supports this:

- `train.py` resumes from `checkpoints-meta/checkpoint.pth`, which `_finalise` wrote at 40k.
- The worker prints `EXTEND` for a `DONE` run below `N_ITERS`.
- The warm-up is `lr·min(step/1000, 1)`, so the lr stays at 1e-4.
- The recipe check ignores `n_iters`.

The cost is ≈ 3.3 A100-h per run, ≈ 100 A100-h in total. What is not ready is everything
downstream that assumed 40k. This ticket fixes those parts, adds a health check for the whole
array, and writes the procedure down.

## Specification (the agent)

1. **Evaluated checkpoints follow the run length.** In `ihdm/metrics/run_eval.py`, `--ckpts all`
   selects every multiple of 5,000 (`EVAL_STRIDE`) that the run holds, up to its largest
   checkpoint: 5k…40k (8) for a 40k run, 5k…60k (12) for a 60k run. It keeps the pilot fallback
   when none is present. `summary.json` records the steps. A 40k run must give byte-identical
   selections to today's `EVALUATED_STEPS`; pin that with a test. Update `05-metrics.md` §8a's
   wording in your log's §6 as a proposal; `main` edits the spec.
2. **The gate follows `N_ITERS`.** `gate.sbatch` defaults to `GATE_EARLY = N_ITERS − 5000` and
   `GATE_LATE = N_ITERS`, and explicit env overrides still win. Gate outputs are named by their
   step pair (`<run_id><amp>_gate_<early>_<late>.{json,tar}`), so the 60k gate never overwrites
   the 40k one. The eval worker unpacks every gate tar of its run, because the cache is
   signature-checked. Keep reading the existing 35k/40k files under their old names: rename them
   on first use, or accept both names. Say which.
3. **Time limits follow the counts.** `submit_eval.sh` computes the default `TIME_LIMIT` of the
   array from `N_ITERS` and `AMP`, using the measured s/chain of `evaluation_plan.md` §2, the
   fixed 0.25 h, a × 1.3 margin and rounding up to 15 min. That gives 60k fp16 = 10,000 chains ≈
   6.99 h → `09:15:00`; 40k values unchanged. `slurm/array/submit_array.sh` accepts `TIME_LIMIT`
   (default unchanged, `11:00:00`), so the extension can ask for `05:00:00` and backfill sooner.
4. **`python -m ihdm.cli.check_array --run-root <root> --cells slurm/array/cells.csv --n-iters N
   [--allow-skips]`** (new). For every cell it reports:
   - `DONE`, and the step in the last `done` event;
   - the EMA checkpoints expected every 2,500 up to N;
   - `full_final.pt`;
   - `abort` events (none allowed) and the skip count;
   - the manifest's `lr` = 1e-4 and `recipe_sha256`, and that the recipe is identical across cells
     apart from the arm keys (`blur_sigma_max`, the schedule name, file and sha) and `seed`;
   - the last train line's step, loss, `grad_norm` and `amp_scale`.

   It prints one table row per cell and a verdict, and exits 0 only if every cell is healthy.
   Reuse `ihdm/train/validate_run.py`; do not duplicate it. Run it read-only on the real Picasso
   run root at the current state (16+ runs done) with `PYTHONPYCACHEPREFIX` on the login node
   (it is light I/O) and paste the output into your log.
5. **Docs.** Add a 60k sizing table (§9) to `evaluation_plan.md`, with per-run hours and
   `--time` for `off` and `fp16`, and campaign A100-h. Document the new env variables and the
   extension in `slurm/eval/README.md` and `slurm/array/README.md`. Add sections to
   `docs/HARNESSES/metrics.md` and `picasso.md` (`check_array` as the array's health harness).
6. **Tests.** `select_checkpoints` for 40k/60k/pilot/missing-step runs; the gate defaults and
   names; the time-limit arithmetic; `check_array` on synthetic run trees (healthy, missing
   checkpoint, abort, recipe drift, wrong lr).
